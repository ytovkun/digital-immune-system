## 1. Загальний огляд

**Мета.** Побудувати й емпірично довести дієвість **цифрової імунної системи
(ЦІС)** — інтелектуального контуру кіберзахисту критичного сервісу розумної
е-держави (**електронне голосування Helios**), який (а) **моделює** сучасні
кіберзагрози за допомогою генеративного ШІ (GenAI) і (б) **захищає** сервіс у
реальному часі, наслідуючи принципи біологічного імунітету.

**Об'єкт дослідження** — процеси забезпечення кібербезпеки сервісів е-держави.
**Предмет** — методи й моделі GenAI-моделювання кіберзагроз та адаптивного
інтелектуального захисту (imunний підхід) для платформи е-голосування.

**Наукова новизна (практичний внесок).**
1. **Дворівнева інлайн-імунна архітектура** (детермінований рефлекс L1 + ШІ-аналіз
   наміру L2) із **детермінованим payload-бэкстопом**, який гарантує, що ШІ
   **неможливо обманути** prompt-injection у бік пропуску однозначної атаки.
2. **Адаптивно→вроджений імунітет** (adaptive→innate): ШІ синтезує сигнатуру
   нового патерну, L1 її **вивчає**, і повторна поява ловиться рефлексом за ~0 мс
   (ефект **імунної пам'яті**, виміряне прискорення **×1257**).
3. **Ко-еволюційний контур «меч vs щит»**: GenAI мутує заблоковані атаки під
   тиском захисту, метрика — частка **утриманих** (held) небезпечних операцій.
4. **Емпіричне head-to-head з реальним сигнатурним SIEM (Wazuh)** на тому самому
   розміченому наборі — доказ переваги поведінкового ШІ-ядра, а не «цифри з
   літератури».

**Ключова теза захисту:** класичний сигнатурний захист (SIEM/IDS) ловить **відомі
payload**, але сліпий до **поведінкових APT**, **prompt-injection проти самого
ШІ-судді** та **held-out новизни**. ЦІС міркує про **намір** і **траєкторію**
актора, тому детектує те, чого немає в жодному списку правил.

## 2. Біологічна аналогія (концептуальна основа)

Архітектура свідомо відображає багаторівневий біологічний імунітет — це не
метафора для краси, а **структурний принцип проєктування**:

| Біологічний імунітет | Компонент ЦІС |
|---|---|
| **Вроджений імунітет** (миттєвий, неспецифічний бар'єр) | **L1 FastReflex** — детермінований блок за сигнатурами/лімітами (~0.05–1 мс) |
| **Адаптивний імунітет** (розпізнавання нового антигену, повільно) | **L2 AIAnalyst** — Claude міркує про намір нового підозрілого запиту (~секунди) |
| **Імунна пам'ять** (антитіла: повторний контакт → миттєва відповідь) | **Кеш вердиктів + навчання L1** — синтезована сигнатура ловить повтор за ~0 мс |
| **Антиген** (маркер «чужого») | **Відбиток клієнта** (`_client_fingerprint`) + payload-сигнатури |
| **Запалення/цитокіни** (сигнал тривоги) | **SOC-алерти + Prometheus-метрики** при перетині порогів |
| **Розпізнавання «свій-чужий»** (толерантність до себе) | **FP-safe дизайн**: пом'якшення замість хард-блоку для неоднозначного (виборця не можна помилково позбавити голосу) |
| **Автоімунна помилка** (атака на своє) | **Хибнопозитив (FP)** — цільова метрика, зведена до **0%** |

## 3. Архітектура системи (два контури)

Система складається з **наступального** (моделювання загроз) і **захисного**
(інлайн-імунітет) контурів, які замикаються в **ко-еволюційний цикл**.

```
        ┌──────────────────────── НАСТУПАЛЬНИЙ КОНТУР (GenAI) ────────────────────────┐
        │  attack_generator → attack_chain → red_team_agent → adaptive_generator      │
        │  (GenAI синтезує атаки, багатокрокові kill-chain, мутує заблоковане)        │
        └───────────────┬─────────────────────────────────────────────┬──────────────┘
                        │ атаки б'ють у :8000                           │ мутації під тиском
                        ▼                                               │
   Клієнт → :8000  ┌─────────────────── ЗАХИСНИЙ КОНТУР (ЦІС) ──────────────────┐
                   │  L1 FastReflex (~0.05мс)  → ALLOW / BLOCK / INSPECT         │
                   │        ↓ INSPECT                                            │
                   │  payload-бэкстоп (детермінований override, тіло до 64КБ)    │
                   │        ↓                                                    │
                   │  L2 AIAnalyst (Claude: намір + траєкторія) → ALLOW / BLOCK  │
                   │        ↓ ALLOW                                              │
                   └──────────────┬─────────────────────────────────────────────┘
                                  ▼ форвард
                            :8001 Helios (справжній e-voting backend)
```

**Розділення портів:** атакувальники завжди б'ють у проксі **:8000**; за ним —
справжній **Helios :8001**. Захист **інлайновий** (in-path): заблокований запит
**фізично не доходить** до Helios (403), а не постфактум-детекція в логах.

## 4. Захисне ядро — детальний опис механізмів

Головний модуль — `immune_system/immune_proxy.py` (реверс-проксі на Flask +
waitress). Кожен запит проходить конвеєр рішень:

### 4.1. Уровень 1 — FastReflex (`fast_reflex.py`)
Детермінований, ~0.05–1 мс, **без ШІ**. Перевіряє:
- **Rate-limit** (запитів/вікно на IP) та **concurrency** (одночасні з'єднання);
- **Сигнатури однозначного payload** у шляху (`L1_HARD_BLOCK`: `/etc/passwd`,
  `union select`, `<script`, `{{`, `${`, `' or '`, `/devlogin/login` …) → BLOCK;
- **Небезпечні HTTP-дієслова** (DELETE/PUT/PATCH до Helios), **адмін-lifecycle**
  (`/delete`, `/archive`, `/keygenerator`), **tally-доступ** без прав;
- **Вивчені від ШІ сигнатури** (adaptive→innate) — ловить повторні атаки миттєво;
- Усе **неоднозначне** → вердикт **INSPECT** (ескалація на L2), а не блок.

### 4.2. Детермінований PAYLOAD-БЭКСТОП (ключова гарантія)
Перед і **незалежно** від рішення ШІ система сканує **шлях І ТІЛО** запиту (до
64 КБ) на однозначний payload (`BACKSTOP_PAYLOADS`). Якщо знайдено — **форс-BLOCK**
навіть якщо ШІ сказав ALLOW. Це закриває два вектори: (1) **prompt-injection**,
що намовляє ШІ пропустити атаку; (2) SQLi/SSTI у **тілі POST**, якого L1 (лише
path) не бачить. Набір бэкстопу **навмисно вузький і FP-safe** (без `..`, `%27`,
`0x`, апострофа — вони бувають у легіт-тексті).

### 4.3. Уровень 2 — AIAnalyst (`ai_analyst.py`)
Claude (модель `claude-opus-4-8`, adaptive thinking, structured outputs).
Аналізує **намір** запиту в контексті **серверних сигналів** (актор не може
підробити):
- `recent_count` — недавня підозріла активність IP (вторинний сигнал);
- `session_validated` — **серверна** валідація cookie у Helios (не клієнтський
  прапорець) з TTL-кешем 30с і **circuit-breaker** (не амплифікувати Helios під флудом);
- `trajectory` — **поведінкова траєкторія** актора (послідовність+темп останніх
  кроків) → детекція багатокрокових APT (recon→логін→дія за секунди);
- `fp_distinct_ips` — скільки **різних IP** за одним відбитком клієнта (виявлення
  **ротації IP** як ухилення);
- `nonhuman_tempo` — прапорець нелюдського темпу (4+ endpoint за <2с).

**Fail-closed для критичних операцій.** За будь-якого збою ШІ (немає ключа /
rate-cap / виняток) критична операція (`/cast`, `/encrypt_tally`, `/freeze` …)
**блокується за замовчуванням**; некритична — пропускається (fail-open).

**Захист ШІ від cache-busting флуду:** ліміт **12 дорогих викликів Claude на IP
за 60с**; понад — критичні → fail-closed, некритичні → ALLOW.

### 4.4. Імунна пам'ять (кеш + навчання L1)
Вердикт BLOCK кешується (TTL 5 хв) за **узагальненим підписом** запиту
(`_signature`: метод + нормалізований шлях, UUID/hash замасковані, query
**зберігається дослівно**). Якщо ШІ повернув signature-токен, що є у шляху, L1
**вивчає** його → наступний такий запит блокується рефлексом за ~0 мс. Саме це
реалізує **adaptive→innate immunity** і дає ефект re-detection (розд. 8.6).

### 4.5. Поведінковий темп (нелюдський темп → ШІ, не хард-блок)
Якщо перед **дією виборця** (login/cast) актор прокрутив **≥4 різних endpoint за
<2с** — це підозра на автоматизовану recon→дію. Свідоме рішення: це **НЕ хард-блок**,
а **ескалація на ШІ** (INSPECT), бо в e-voting хибне блокування = **позбавлення
голосу**. ШІ бачить повну траєкторію (+прапор темпу) і відрізняє recon-sweep від
швидкого-але-легітимного виборця.

### 4.6. Захист даних та приватність
- **Інспекція відповідей (анти-ексфільтрація):** аномально великий дамп на
  `/voters/`, `/ballots/` → позначка (soft) або блок (hard, вимкнено за
  замовчуванням, FP-safe);
- **Маскування PII у журналі** (`_redact_pii`): voter_uuid/ballot_hash не
  зв'язуються з дією/часом (таємниця голосування);
- **Огрублення ballot-timestamp** до години у відповідях — проти
  timing-деанонімізації виборця;
- **Security headers + CSP** у кожній відповіді (XSS, clickjacking, MITB/CDN);
- **XFF→Helios overwrite**: проксі — межа довіри, переписує X-Forwarded-For на
  реальний IP (клієнтський спуфнутий XFF не отруїть логи/rate-логіку Helios).

### 4.7. Стійкість та спостережуваність
- **SSRF/path-escape guard** (`_safe_backend_url`): нормалізація шляху,
  заборона `..`, абсолютних URL, host-check;
- **Memory-DoS захист**: евікція застарілих ключів у всіх структурах
  (IP-вікна, траєкторії, відбитки, кеш, сесії), межі `MAX_TRACKED_IPS`;
- **Ротація журналів** за розміром; **таймаут форварду** 10с (анти
  thread-starvation);
- **SOC-алерти** (лог-попередження при перетині порогів) + **Prometheus**
  ендпойнт `/__immune__/metrics` (scrape для Grafana/SOC);
- **`/__immune__/stats`** — JSON-метрики в реальному часі (для дашборда).

## 5. Наступальний контур (GenAI-моделювання загроз)

- **`attack_generator.py`** — GenAI синтезує різнокласові атаки на Helios
  (SQLi, XSS, SSTI, traversal, CSRF-trustee, ballot-stuffing, APT-розвідка,
  соц-інженерія тощо) з MITRE ATT&CK-прив'язкою.
- **`attack_chain.py`** — багатокрокові ланцюги **Cyber Kill Chain**
  (Reconnaissance→Weaponization→Delivery→Exploitation→Installation→Action).
- **`red_team_agent.py`** — виконує атаки проти цілі (baseline :8001 або
  defended :8000), пише покрокові звіти.
- **`adaptive_generator.py`** — **ко-еволюція**: бере заблоковані атаки й **мутує**
  їх (режими `escalate`/`refine`/`bypass`), **зберігаючи шкідливу ціль** (принаймні
  один крок мусить спробувати критичну операцію — інакше «обхід» був би вакуумним).

**Класи атак у наборі (11):** `ballot_stuffing`, `csrf_trustee_takeover`,
`dos_zk_flood`, `session_forgery`, `tally_manipulation`, `voter_coercion_receipt`,
`voter_device_js_injection`, `voter_phishing_credential`,
`voter_social_engineering_vote_change`, `voter_suppression_targeted`,
`voter_timing_deanonymization`.

## 6. Immune Response Engine та класифікація ризику

- **`immune_response_engine.py` (IRE)** — класифікує кожну атаку та зіставляє з
  імунною відповіддю (рівень загрози, рекомендована реакція).
- **`risk_scorer.py`** — скорить ризик (severity × ймовірність), базовий та
  адаптивний варіанти. У наборі **22 атаки** (11 базових + 11 адаптивних).

## 7. Прив'язка до MITRE ATT&CK та Cyber Kill Chain

Кожна атака має `mitre_technique_id`/`mitre_technique_name`; kill-chain-звіт
(`core/attack_flow.py` → `reports/killchain/attack_flow.json`) розкладає атаку по
фазах із **вердиктом на кожен крок** (4 кольори): `blocked` / `leaked`
(критична операція дійшла) / `allowed` (безпечний крок) / `simulated`.

| Accuracy | **1.0** | [0.963, 1.0] |
| **FPR** | **0.0** | — |
| FNR | 0.0 | — |
| ROC-AUC | **1.0** | — |

Матриця плутанини: TP=40, FN=0, FP=0, TN=61.

### 8.2. Гранична стрес-вибірка + реалістичний ROC (n=12)
Неоднозначні кейси (6 легіт-з-підозрілими-ознаками + 6 тонких атак без явного
payload) — **чесний** тест дискримінації:
- Precision **1.0**, Recall **0.667**, F1 **0.8**, AUC (гранична) **0.75**;
- Матриця: TP=4, FN=2, FP=0, TN=6;
- **Комбінований ROC-AUC = 0.977** (основна+гранична) — реалістична крива, не
  «ідеальний» 1.0, що підкреслює **чесність методології**.

### 8.3. Детекція APT (n=3 поведінкові ланцюги)
Усі **3/3** заблоковано (статус 403):
1. recon→login (автоматизований збір + логін за секунди);
2. систематичний обхід endpoint'ів (sweep) → логін виборця;
3. розвідка trustees → доступ до підрахунку.

### 8.4. Ефективність захисту: baseline vs defended
- **Baseline** (атаки прямо в Helios :8001): критичні операції **проходять**
  (0 заблоковано);
- **Defended** (через ЦІС :8000): **16/16 критичних операцій заблоковано**,
  **витоків (leaked) = 0**, нейтралізовано 10, off-server 1.

### 8.5. Ко-еволюція «меч vs щит»
- **gen-0** (вихідні атаки): 11 атак, 16 критичних спроб → **held 100%**, leaked 0;
- **gen-1** (мутовані GenAI під тиском блокувань): 11 атак, **22 критичні спроби**
  → **held 100%**, leaked 0;
- За режимами: **bypass** 7 атак (11 крит-оп, 100% блок), **refine** 4 атаки
  (100% блок). Мутації **не пробили** захист.

### 8.6. Re-detection (імунна пам'ять, n=4 патерни × 3 зустрічі)
- 1-ша зустріч (новизна, ШІ): **3927 мс** середньо;
- Повторна (пам'ять, L1): **3.1 мс** середньо;
- **Прискорення ×1257**; **8/8** повторних спіймано рефлексом L1;
- **4 сигнатури** вивчено L1 від ШІ під час експерименту.

### 8.7. Порівняння з реальним SIEM (Wazuh) — Таблиця 3.E
На **тому самому** розміченому наборі (кореляція за маркером `_bid`):

| Метрика | SIEM (Wazuh) | ЦІС (це дослідж.) |
|---|---|---|
| Precision | 1.0 | 1.0 |
| **Recall / Detection** | **0.225** | **1.0** |
| F1 | 0.367 | 1.0 |
| FPR | 0.0 | 0.0 |
| **APT (поведінка)** | **0/3** (за побудовою*) | **3/3** |

Матриця Wazuh: TP=9, FN=**31**, FP=0, TN=61 — **пропустив 31 атаку**.
\* «0/3 за побудовою» — структурне обмеження: сигнатурний SIEM **не має
correlation-правила** на багатокрокову траєкторію; окремі кроки APT без payload
не тригерять web-attack правила. Це якісна, а не лише кількісна перевага ШІ-ядра.

## 14. Обмеження та майбутня робота

**Свідомі обмеження (чесна методологія):**
- Допоміжні експерименти (re-detection, APT, гранична) мають **малий n** —
  демонструють механізм; статзначущі показники з ДІ — лише для основного
  бенчмарку (n=101);
- **Кеш-компроміс:** AI-FP на аномалію в шляху персистить на TTL (5 хв) для того
  самого query — не породжує нових FP, не впливає на FPR (див.
  `methodology_notes.md`);
- **SIEM APT 0/3 — за побудовою** (немає correlation-правила), не вимір;
- SIEM-прогон і кампанія — окремі запуски на **спільному** наборі (не один
  атомарний прогон); manifest фіксує стан.

**Напрями розвитку:** розширення вибірок допоміжних експериментів; додавання
Suricata (мережевий IDS) поряд із Wazuh; онлайн-навчання L1 з довшою пам'яттю;
розгортання поверх TLS (активація HSTS); федеративний обмін сигнатурами між
інстансами (колективний імунітет).

## 15. Ключові тези для захисту (summary)

1. **Інлайн-імунітет, не постфактум-детекція**: атака фізично не доходить до Helios.
2. **ШІ неможливо обманути** завдяки детермінованому payload-бэкстопу.
3. **Adaptive→innate**: пам'ять дає **×1257** прискорення повторної детекції.
4. **Ко-еволюція**: мутації GenAI **не пробили** захист (held 100% у gen-0 і gen-1).
5. **Емпірична перевага над реальним SIEM**: Recall 1.0 vs 0.225, APT 3/3 vs 0/3.
6. **FP=0** при повній детекції — критично для e-voting (жодного позбавлення голосу).
7. **Чесна методологія**: комбінований ROC 0.977 (не «ідеальний» 1.0), явні n,
   задокументовані компроміси, відтворюваність через manifest.
